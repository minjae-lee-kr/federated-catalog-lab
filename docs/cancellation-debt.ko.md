# 응답은 끝났지만, 작업은 끝나지 않았다

[English](cancellation-debt.md) · [프로젝트 소개](../README.ko.md)

느린 의존성이 타임아웃되는 것보다 더 어려운 문제는, **동시 실행 제한기가 정상으로 보이는데도 제한해야 할 작업은 계속 쌓이는 상황**입니다.

이 실험은 Apollo Federation 게이트웨이와 세 HTTP 서브그래프를 사용합니다. 재고 작업은 타이머로 모사하지만, HTTP 요청과 연결 종료, 취소 신호 전달은 실제로 실행합니다. DB 성능이나 실서비스 부하를 측정하는 실험은 아닙니다.

```sh
pnpm install --frozen-lockfile
pnpm verify
pnpm debt
# 한·영 인터페이스: http://127.0.0.1:4182/
pnpm debt:ui
# 변경 사항이 없는 커밋에서 읽기 전용 기록 생성
pnpm debt:export
```

`pnpm debt`는 `.local/cancellation-debt.json`에 GraphQL 응답, 순서가 있는 작업 이벤트, 독립 검사 결과, 런타임 정보, 소스 목록과 실행 전후 변경 여부를 저장합니다. `pnpm debt:ui`는 새로운 실험을 실행하고 그 근거를 내려받는 화면입니다. 저장된 성공 결과를 재생하는 화면이 아닙니다.

`pnpm debt:export`는 별도 기능입니다. 변경 사항이 없는 Git 커밋에서 새 실험을 실행하고, 결과가 성립했는지와 화면 생성 뒤 소스·HEAD가 그대로인지 확인한 후 `.local/cancellation-export/`에 저장합니다. `index.html`을 직접 열거나 해당 디렉터리를 정적 파일로 제공할 수 있습니다. 상대 경로의 표시 파일, 원본 `report.json`, 같은 데이터를 담은 `report-data.js`, 파일 해시를 담은 `export.json`이 포함됩니다. 화면에 기록 시각·소스 버전·한계를 표시하고 실행 버튼과 실시간 통신 코드는 제외합니다. API가 필요하지 않으며 콘텐츠 보안 정책도 네트워크 연결을 차단합니다. 외부에 게시하는 명령은 아닙니다. 원본 JSON은 바꾸지 않으며 해시는 파일 식별과 재현을 돕지만 실행의 진위를 인증하지 않습니다.

## 정상으로 보이는 카운터의 반례

같은 **조회**를 순차적으로 네 번 시도합니다. 서브그래프 응답 기한은 160ms, 재고 작업은 1,000ms이며, 실행 제한을 적용하는 조건의 허가는 두 개입니다. 작업 수명의 겹침을 드러내기 위한 설정값으로, 운영 권장값이 아닙니다.

첫 로컬 실행에서 다음 결과를 관측했습니다.

| 정책                                        | 최대 실행 작업 | 최대 사용 허가 | 마지막 응답 뒤 남은 작업 | 완료 / 취소 / 거절 |
| ------------------------------------------- | -------------: | -------------: | -----------------------: | ------------------ |
| 타임아웃만 적용                             |              4 |              4 |                        4 | 4 / 0 / 0          |
| 요청자 타임아웃에 허가 반환 — 잘못된 대조군 |              4 |              1 |                        4 | 4 / 0 / 0          |
| 작업 종료까지 허가 유지                     |              2 |              2 |                        2 | 2 / 0 / 2          |
| 작업 종료까지 허가 유지 + 협력적 취소       |              1 |              1 |                        0 | 0 / 4 / 0          |

관측한 한 실행의 결과이며 화면에 고정한 값이나 다른 환경에 대한 보장이 아닙니다. 다시 실행해 원본 기록을 확인할 수 있습니다. 예상한 반례가 나타나지 않거나 실행 중 소스가 바뀌면 실험은 실패를 표시합니다.

두 번째 조건은 일부러 잘못 구현했습니다. 응답을 기다리던 HTTP 연결이 사라질 때 허가를 반환하지만, 취소 신호를 무시하는 작업은 계속 실행됩니다. 허가 수는 두 개 미만으로 보이는데 실제 작업은 네 개까지 겹칩니다. `permits <= capacity`만 검사하면 잘못된 구현도 통과합니다.

세 번째 조건은 타이머가 실제로 종료될 때까지 허가를 유지합니다. 작업이 취소를 무시해도 실제 실행량은 제한됩니다. 그 대가로 남은 작업이 자리를 차지하는 동안 추가 요청을 거절합니다. 네 번째 조건은 취소를 지원하는 타이머를 종료하고, **그 종료 이후에** 허가를 반환합니다.

**실행 허가는 호출자가 기다리는 시간보다, 처리 용량을 소비하는 작업의 수명을 따라야 합니다.** `Promise.race`로 타임아웃을 반환한 뒤 호출자의 `finally`에서 허가를 반환해도, 나머지 Promise가 계속 실행된다면 같은 문제가 생길 수 있습니다.

## 취소 신호가 전달되는 과정

```text
응답이 끝나기 전에 호출자가 연결 종료
  → Node ServerResponse의 close + !writableFinished
  → 게이트웨이 context의 요청별 AbortSignal
  → RemoteGraphQLDataSource에서 fetch에 신호를 명시적으로 전달
  → 재고 서버에서 HTTP 응답의 조기 연결 종료 관측
  → 취소를 지원하는 타이머가 reject
  → 실제 작업 종료
  → 실행 허가 반환
```

재고 서버에는 별도로 생성한 절대 기한도 전달합니다. 직접 HTTP로 호출하는 검증에서는 연결을 유지한 상태에서 이 기한만으로 타이머가 취소되는지 확인합니다. 기한은 재고 fetch를 시작할 때 계산하며 **사용자 요청 전체의 시간 예산이 아닙니다.** 같은 호스트의 시계를 사용합니다. 분산 환경에서는 기한의 신뢰 정책과 시계 오차에 대한 별도 가정이 필요합니다.

`IncomingMessage.close`는 취소 신호로 사용하지 않습니다. 요청 본문을 다 읽었다는 사실은 호출자가 결과를 포기했다는 뜻이 아니기 때문입니다. `ServerResponse.finish` 역시 상대가 응답을 받았다는 증거는 아닙니다. 이 구현은 응답 연결의 조기 종료를 관측하며 이를 업무 처리의 롤백 보장으로 해석하지 않습니다.

Apollo Gateway가 이 연결 관계를 자동으로 추론하지는 않습니다. 고정한 버전의 `RemoteGraphQLDataSource`는 fetch 요청을 직접 구성합니다. 이 실험은 공개 확장 지점인 `process`와 `fetcher`, 그리고 `AsyncLocalStorage`를 사용해 동시 호출 사이에서도 올바른 요청의 신호를 전달합니다. 한 호출자만 중단하고 이웃 호출자는 정상 완료하는 검증으로, 공유 변수에 저장한 취소 신호가 다른 요청에 섞이는 오류가 생기지 않는지 확인합니다.

취소는 하위 작업의 협조가 필요합니다. 허가만 유지하는 조건과 잘못된 조기 반환 조건은 신호를 의도적으로 무시하며, HTTP 응답이 끝난 뒤에도 작업이 계속됩니다. DB 드라이버, CPU 연산, 외부 서비스나 이미 커밋한 부수 효과까지 중단할 수 있음을 보이지는 않습니다. 모든 서비스가 하나의 이벤트 루프를 공유하므로 이를 막는 작업은 취소와 타임아웃의 처리도 지연시킵니다.

## 응답이 사라진 뒤의 작업을 관측하기

응답에만 붙이는 관측 정보로는 응답 채널 종료 뒤 계속되는 작업을 보고할 수 없습니다. 따라서 별도의 프로세스 내부 이벤트 기록을 유지합니다. `admitted`, `cancel-requested`, `completed`/`cancelled`, `permit-released`, `caller-completed`를 서로 다른 전이로 기록합니다. **취소를 요청했다는 사실을 취소 완료로 세지 않습니다.**

`cancellation-check.ts`는 이벤트로 활성 작업과 소유한 허가를 독립적으로 재구성합니다. 카운터, 요청·작업 식별자, 작업별 종료 횟수와 최종 정리를 검사합니다. 네 HTTP 응답에 포함된 요청 식별자를 정확한 검사 대상으로 받아, 각 요청에 진입 또는 거절 기록과 한 번의 호출자 완료가 있는지 확인합니다. 여기에 없는 요청의 작업도 허용하지 않습니다. 작업이 호출자 완료보다 먼저 시작한다고 가정하지 않고 전체 기록을 연결합니다.

실제 작업 한도 초과와 작업 종료 전 허가 반환을 따로 보고하므로, 잘못된 대조군을 하나의 ‘통과’ 표시 뒤에 숨기지 않습니다. 합계 변경, 종료 이벤트 누락, 반환 사유 변경, 호출자 완료 중복·누락을 만드는 변조 검증을 포함합니다. 실제 HTTP 대조군 두 개는 응답의 요청 식별자만 바꾸거나 전달된 작업 식별자만 제거합니다. 원래의 부분 GraphQL 데이터가 남아 있어도 근거 검증은 실패해야 합니다.

검사기는 이벤트가 빠짐없이 기록됐다는 가정을 신뢰합니다. 기록되지 않은 작업이나 악의적인 실행 환경까지 검출하지는 않습니다. 소스 해시도 실행 인증은 아닙니다. 처리 한도는 단일 재고 프로세스의 한도이며 여러 복제본 전체에 대한 보장이 아닙니다.

네 조건 모두 상품·판매자 필드는 남습니다. 재고 조회 실패는 `null`과 명시적 오류로 표시하며 ‘품절’로 바꾸지 않습니다. 협력적 취소가 만드는 GraphQL 오류와 게이트웨이 fetch 타임아웃은 경합할 수 있으므로, 보고서는 실제 관측한 오류 코드를 보존하고 항상 같은 순서를 주장하지 않습니다.

## 공식 문서와 확인한 구현

- [Node 24.19 HTTP](https://nodejs.org/download/release/v24.19.0/docs/api/http.html#event-close_2): 응답 연결 종료, 요청 완료, `writableFinished`의 의미를 구분합니다.
- [Node 24.19 타이머](https://nodejs.org/download/release/v24.19.0/docs/api/timers.html#cancelling-timers): Promise 기반 타이머는 취소 신호를 받아 reject할 수 있습니다.
- [Node 24.19 비동기 문맥](https://nodejs.org/download/release/v24.19.0/docs/api/async_context.html): 요청별 비동기 상태를 분리합니다.
- [Apollo Server 통합 계약](https://www.apollographql.com/docs/apollo-server/integrations/building-integrations): HTTP 경계와 context 생성은 통합 코드가 담당합니다.
- [Apollo Gateway API](https://www.apollographql.com/docs/apollo-server/using-federation/api/apollo-gateway): 데이터 소스 확장 지점입니다. 설치한 `@apollo/gateway@2.14.4/dist/datasources/RemoteGraphQLDataSource.js`의 요청 구성과 fetcher 동작을 확인했으며 비공개 메서드를 재정의하지 않습니다.
