# 오류는 사라졌는데, 재확인은 실패했습니다

[English](react-recheck.md) · [앞선 캐시 실험](client-cache.ko.md)

재고 조회가 실패했는데 화면에는 여전히 **3개**가 보였습니다. 이어서 캐시를 읽자 오류 표시도 사라졌습니다. 그 사이 서버로 보낸 요청은 **0건**이었습니다.

이 화면에서 “다시 확인했습니다”라고 안내해도 될까요?

가상 상품 세 개를 사용하는 Apollo Client·React 실험입니다. 정상 응답을 한 번 받은 컴포넌트를 유지한 채 재고 조회를 실패시키고, 그다음 같은 쿼리를 캐시에서 읽었습니다. 관심사는 캐시를 무조건 없애는 방법이 아닙니다. **사용자가 보던 값을 유지하면서, 실패한 재확인을 성공으로 오해하게 하지 않을 방법**입니다.

먼저 아래의 세 단계를 비교하고, `data`와 `previousData`가 왜 같은 이력을 뜻하지 않는지 살펴봅니다. 마지막에는 표시할 값과 서버 조회 시도를 나눠 관리할 때 생기는 비용을 다룹니다.

## 무엇을 바꾸고, 무엇을 유지했나

Apollo Client는 서버에서 읽은 값을 메모리 캐시에 저장합니다. `useQuery`는 쿼리의 상태를 React 컴포넌트에 전달합니다. 이 실험에서는 상품 목록과 가격은 정상으로 두고, 램프 상품의 `availability` 조회만 실패시켰습니다. 응답에는 다른 상품의 데이터와 함께 램프의 `availability: null`, 해당 필드의 GraphQL 오류가 들어 있습니다. HTTP 상태는 200입니다.

`null`은 재고가 0이라는 뜻이 아닙니다. 이번 응답으로 수량을 확인하지 못했다는 뜻입니다. 앞서 받은 수량 `3`이 지금도 맞는지는 실험에서 알 수 없습니다.

각 정책마다 새 클라이언트와 캐시를 만들고, 한 컴포넌트를 아래 순서로 유지했습니다.

| 단계 | 실행한 일 | 실제 HTTP 요청 |
| --- | --- | ---: |
| 정상 조회 | `network-only`로 정상 서버에서 수량 `3`을 받음 | 1 |
| 실패 조회 | 같은 observable을 `network-only`로 다시 평가. 이번에는 실패 서버 사용 | 1 |
| 캐시 읽기 | 같은 observable을 `cache-first`로 다시 평가. 실패 서버는 그대로 선택된 상태 | 0 |

두 번째와 세 번째 단계는 `useQuery`가 반환한 `observable.reobserve(...)`를 직접 호출합니다. 일반적인 `useQuery.refetch()` 버튼이나 자동 재시도의 동작을 재현한 것은 아닙니다. `cache-first`는 필요한 데이터를 캐시에서 읽을 수 있으면 서버에 요청하지 않는 정책입니다.

핵심 호출은 아래와 같습니다. 서버 전환과 기록 수집을 생략한 설명용 코드입니다.

```js
// useQuery가 반환한 같은 observable을 유지합니다.
try {
  await observable.reobserve({ fetchPolicy: 'network-only' });
} catch (error) {
  // 실제 관측기는 이 오류도 기록합니다.
}
await observable.reobserve({ fetchPolicy: 'cache-first' });
```

앞선 [Promise 기반 실험](client-cache.ko.md)은 `client.query()`의 반환값과 캐시를 관측했습니다. 이번에는 실제 `useQuery` 컴포넌트의 DOM까지 확인합니다. 별도의 `watchQuery` 구독, 메서드가 반환하는 Promise, React hook 결과는 서로 다른 관측 지점이므로 같은 결과 객체처럼 취급하지 않았습니다.

## 실패한 요청과 화면에 남은 값은 서로 다른 사실이었다

`errorPolicy`는 GraphQL 오류와 부분 데이터를 어떻게 다룰지 정합니다. 정상 조회 뒤 실패했을 때, 고정한 버전의 두 정책은 다음과 같이 달랐습니다.

| 실패 직후 | `all` | `none` |
| --- | --- | --- |
| 현재 `data`의 램프 재고 | 새 응답의 `null` | 이전 수량 `3` |
| `previousData`의 램프 재고 | 이전 수량 `3` | `previousData` 없음 |
| `error.data`의 램프 재고 | 새 응답의 `null` | 새 응답의 `null` |
| `reobserve`의 Promise | 데이터와 오류를 담아 resolve | 오류로 reject |
| hook 상태 | `networkStatus: 8`, `dataState: complete` | `networkStatus: 8`, `dataState: complete` |

`none`에서 Promise가 거절됐다는 사실만 읽으면 화면에도 데이터가 없을 것이라 예상하기 쉽습니다. 하지만 실제 상품 카드에는 이전 수량 `3`이 남아 있었습니다. 새 부분 응답은 `error.data`에서 따로 확인할 수 있었습니다.

특히 `previousData`가 비어 있다는 점이 중요했습니다. 이름만 보고 이 필드를 “화면에 남아 있는 과거 데이터”의 표시로 쓰면 이 사례를 놓칩니다. 현재 `data` 자체가 이전 값을 유지할 수 있기 때문입니다. `previousData`의 유무만으로 값의 출처나 확인 시점을 판정할 수는 없었습니다.

`dataState: complete`도 재고 재확인의 성공 여부와는 달랐습니다. 두 정책 모두 `complete`였지만 오류가 있었고, 표시한 재고도 서로 달랐습니다. 데이터가 읽힐 수 있는 상태와 그 데이터로 어떤 안내를 해도 되는지는 별도로 판단해야 했습니다.

## 오류가 없어진 이유는 새 성공 응답이 아니었다

마지막 `cache-first` 호출 뒤에는 두 정책 모두 현재 hook 결과에서 오류가 사라졌고, `networkStatus`는 7이 됐습니다. `all`은 `null`, `none`은 `3`을 그대로 읽었습니다. 실제 HTTP 요청은 없었습니다.

여기서 서버가 복구했다고 말할 근거는 없습니다. 실패한 필드를 다시 조회하지 않았기 때문입니다. 그렇다고 `3`이 틀렸다고 단정할 근거도 없습니다. 이 실험에는 재고 변경이나 예약이 없습니다.

`all`을 선택하면 다른 상품을 계속 보여 주면서 확인할 수 없는 필드를 `null`로 남길 수 있습니다. 대신 UI는 확인 불가와 품절을 구분해야 합니다. `none`에서는 기존 화면을 유지할 수 있었지만, 그 값이 방금 확인된 값처럼 보이지 않도록 해야 합니다. 어느 쪽도 오류 정책 하나로 재고의 유효성을 결정해 주지는 않습니다.

## 값을 지우는 대신, 확인한 일을 따로 기록한다면

검토한 설계는 작은 상태 분리입니다. 화면에서 읽을 수 있는 값과 마지막 명시적 서버 조회 시도를 따로 둡니다.

```text
표시할 값: 3
마지막 서버 조회: 실패
마지막 성공 때 받은 값: 3
현재 실제 재고: 이 기록만으로는 알 수 없음
```

고려할 수 있는 규칙은 이렇습니다. 새 조회를 시작하면 `pending`, 결과를 받으면 성공이나 실패로 기록합니다. 캐시 읽기는 표시할 값을 바꿀 수 있지만 서버 조회의 성공을 새로 만들거나 실패를 지우지 않습니다. 이 규칙이라면 마지막 캐시 읽기 뒤에도 실패를 안내할 수 있습니다. **여기부터는 관측에서 출발한 설계 제안입니다. 공개 실험에 이 상태 관리를 통합하거나 효과를 검증하지는 않았습니다.**

이 분리는 상태를 하나 더 저장하는 것으로 끝나지 않습니다.

- **무엇을 성공으로 볼 것인가.** 이 예에서는 램프 재고 필드의 확인 여부를 봅니다. HTTP 200이나 Promise의 resolve만으로는 충분하지 않습니다. 부분 응답에서 어떤 필드의 확인을 요구할지 호출자가 정해야 합니다.
- **실패를 언제 지울 것인가.** 캐시에서 값이 읽혔다는 이유로 지우지 않으면 안내가 더 오래 남습니다. 다음 성공, 상품 변경, 사용자의 닫기 동작 중 무엇으로 지울지 정해야 합니다. 실패를 숨기지 않는 대가로 화면의 복잡도가 늘어납니다.
- **늦게 도착한 결과를 어떻게 처리할 것인가.** 나중에 시작한 시도가 있으면 이전 시도의 늦은 완료를 조회 기록에서 제외할 수 있습니다. 그러면 유용한 성공 결과도 버리게 됩니다. 서버의 응답 버전이 있다면 다른 규칙을 고를 수 있습니다.

시도 순번을 조회 기록에 붙이는 것만으로 표시 값의 응답 순서까지 보호되지는 않습니다. 상품·사용자·변수의 범위가 바뀔 때 기록을 언제 초기화할지도 정해야 합니다. 이번의 순차 실험으로는 이런 경합과 수명 관리의 적절성을 판단할 수 없습니다.

이 상태가 있어도 주문을 허용해도 되는지는 알 수 없습니다. 주문 가능 여부에는 서버의 재검증이나 예약처럼 별도의 계약이 필요합니다. 여기서 다룬 것은 사용자가 읽는 화면의 설명 책임입니다.

## 화면까지 확인하려면 JSON 비교만으로는 부족했다

관측기는 `useLayoutEffect`에서 commit 뒤 실제 컴포넌트 DOM을 읽습니다. hook 값, 상품 카드의 숫자와 상태, 오류 문구, Promise 결과, 메모리 캐시, 서버·브라우저 양쪽의 HTTP 응답 원문을 서로 대조했습니다. [React의 render와 commit 구분](https://react.dev/learn/render-and-commit)에 따라 이 기록을 렌더 횟수로 부르지 않습니다. 연속한 동일 DOM은 생략하며, 전체 commit이나 paint 횟수도 측정하지 않습니다.

초기 검사에서 놓친 부분도 있었습니다. DOM 안에 들어 있는 진단용 JSON만 맞으면 상품 카드 숫자가 잘못돼도 통과할 수 있었습니다. 그래서 실제 카드와 상태표의 표시 값도 따로 대조하도록 검사를 강화했습니다. 카드나 상태표의 `3`을 `999`로 바꾼 사본은 거절돼야 합니다. 기록 안에 올바른 값이 있다는 사실과 사용자가 읽는 위치에 올바르게 표시됐다는 사실은 달랐습니다.

실험은 Apollo Client 4.3.3, React 19.3.1의 production build, StrictMode 없이 유지한 컴포넌트, 고정된 쿼리·변수·메모리 캐시를 사용합니다. `reobserve` 뒤의 종료 조건은 해당 단계의 로딩이 끝난 DOM과 타이머 한 턴입니다. 모든 비동기 작업이 끝났다는 보장은 아닙니다.

재마운트, StrictMode, Suspense, SSR, 변수 변경, 영속 캐시, 전송 계층 오류와 동시 요청은 이 결과의 범위 밖입니다. 제품의 장애를 재현한 사례가 아니라, 가상 입력과 실제 HTTP를 사용하는 개인 실험입니다.

캐시는 화면을 계속 보여 줄 수 있게 했습니다. 그 화면에서 “다시 확인했다”고 말하려면, 값을 읽을 수 있다는 사실 외에 **확인 시도가 어떻게 끝났는지**도 필요했습니다.

## 직접 실행하고 기록 읽기

[실행 안내](../experiments/react-recheck/README.ko.md)에서 고정된 의존성 설치와 로컬 관측 서버 실행 방법을 확인할 수 있습니다. 실제 브라우저에서 각 정책의 정상 조회 → 실패 조회 → 캐시 읽기를 순서대로 실행하고, 새 기록을 저장합니다. 기존 기록에 새 실행 결과를 덮어쓰지 않습니다.

기록을 읽을 때는 실패 단계의 HTTP 응답에서 출발해 `data`, `previousData`, `error.data`, 실제 상품 카드 순서로 대조해 보세요. 그다음 마지막 단계의 요청 수가 0인지 확인하면, 오류가 없어졌다는 사실과 서버 조회가 성공했다는 주장을 분리해서 볼 수 있습니다.
