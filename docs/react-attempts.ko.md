# 늦은 응답을 무시했는데, 화면의 값은 바뀔 수 있을까?

[English](react-attempts.md) · [앞선 React 관측](react-recheck.ko.md)

재확인이 실패하면 이전 값을 유지하면서 실패 안내를 남길 수 있습니다. 그런데 먼저 시작한 요청의 성공 응답이 나중에 도착하면 어떨까요? “이 시도는 더 이상 유효하지 않다”는 검사로 상태 갱신을 건너뛰면, 화면의 숫자도 보호될까요?

문제는 값이 화면에 도착하는 경로가 하나가 아니라는 데 있습니다. 직접 관리하는 조회 상태는 Promise 콜백에서 갱신할 수 있지만, 상품 값은 Apollo의 공유 캐시를 통해 React에 전달됩니다. 콜백의 조건문이 그보다 먼저 일어난 캐시 쓰기까지 막아 주지는 않습니다.

이 실험은 **조회 상태만 보호하는 방식**과 **캐시에 쓰기 전에도 같은 검사를 하는 방식**을 비교합니다. 가상의 상품·창고, 실제 GraphQL HTTP, React 컴포넌트를 사용합니다. 먼저 응답이 통과하는 두 경로를 읽고, 상품 전환과 응답 순서가 달라지는 사례를 비교한 뒤, 직접 쓰기를 관리할 때의 비용을 살펴보세요.

## 같은 조건문을 어디에 두는가

두 방식 모두 현재 화면의 범위와 마지막 시도를 따로 관리합니다. 범위는 상품 SKU와 창고의 조합입니다. 범위를 바꿀 때마다 세대 번호를 올리고, 조회를 시작할 때마다 시도 번호를 붙입니다. 응답이 도착했을 때 세 값이 현재 상태와 맞아야 조회 상태를 갱신합니다.

비교를 위해 한쪽의 검사 조건을 약하게 만들지 않았습니다. 차이는 Apollo가 캐시에 쓰는 시점입니다.

| 방식 | HTTP 조회 | 캐시 쓰기 | 조회 상태 |
| --- | --- | --- | --- |
| 상태만 보호 | `client.query`의 `network-only` | Apollo가 응답을 자동 반영 | 완료 콜백에서 현재 시도인지 검사 |
| 쓰기도 보호 | `client.query`의 `no-cache` | 현재 시도임을 확인한 뒤 명시적 `writeQuery` | 같은 검사와 쓰기 뒤에 반영 |

React 화면은 `cache-only` 쿼리로 캐시를 읽습니다. 네트워크 요청은 명령 경로에서 시작하고, 화면은 캐시 변경을 구독합니다. 따라서 조회 상태를 바꾸지 않았는데도 캐시 경로로 숫자가 달라질 수 있는지 구분해서 볼 수 있습니다.

앞선 실험은 한 `useQuery`의 `observable.reobserve`를 순차적으로 호출했습니다. 이번에는 서로 겹치는 독립 요청을 비교하려고 `client.query` 명령과 캐시 구독 화면을 분리했습니다. 일반적인 `refetch`나 앞선 hook의 수명 주기 전체를 검증하는 실험은 아닙니다.

상태 모형은 현재 범위·세대·마지막 시도만 관리합니다. 별도의 마지막 성공 이력은 저장하지 않습니다. 범위를 바꾼 뒤 캐시에 값이 있어도 시도 상태는 `idle` 또는 `pending`일 수 있습니다. 읽을 수 있는 값과 이 방문에서 확인한 결과를 같은 것으로 취급하지 않습니다.

[Apollo의 `no-cache`](https://www.apollographql.com/docs/react/caching/advanced-topics)는 응답의 자동 캐시 쓰기를 생략합니다. [명시적 `writeQuery`](https://www.apollographql.com/docs/react/caching/cache-interaction)는 로컬 캐시를 바꿉니다. 서버의 재고를 변경하거나 예약하는 API가 아닙니다.

## 실패해야 할 사례만 고르지 않는다

다섯 사례를 두 방식으로 실행합니다. 각 실행은 새 클라이언트와 캐시로 시작하고, 실제 HTTP 응답으로 A·동쪽 창고의 수량 `3`을 먼저 받습니다. 그다음 응답을 아래 순서로 풀어 줍니다. 수량은 순서를 식별하기 위한 가상 값입니다.

| 사례 | 통제한 순서 | 비교하려는 경계 |
| --- | --- | --- |
| 늦은 성공 | 먼저 시작한 요청을 보류 → 새 요청 실패 → 이전 요청의 `7` 도착 | 실패 상태를 유지해도 캐시 값이 바뀌는가 |
| 상품 변경 | A 요청 보류 → B로 이동 → B의 `12` 도착 → A의 `7` 도착 | 다른 상품의 캐시가 현재 화면과 분리되는가 |
| 창고 변경 | A·동쪽 요청 보류 → A·서쪽으로 이동 → 서쪽 `12` → 동쪽 `7` | 같은 상품이라도 변수가 바뀐 범위를 구분하는가 |
| A → B → A | 첫 A 요청 보류 → B → A로 복귀 → 새 A의 `9` → 첫 A의 `7` | 같은 캐시 키로 돌아왔을 때 방문 세대도 필요한가 |
| 실패 뒤 캐시 읽기 | 새 요청 실패 → `cache-only` 조회 | 캐시 읽기가 독립적인 실패 상태를 지우는가 |

상품·창고를 바꾸는 사례에서는 두 방식 모두 현재 화면을 유지할 수 있습니다. 올바른 캐시 식별만으로 이미 해결되는 상황을 구분하기 위한 대조입니다. 마지막 사례도 “캐시를 읽으면 언제나 실패 기록이 사라진다”는 과한 일반화를 막기 위해 둡니다. 오류를 hook 결과에만 맡긴 앞선 실험과 달리, 여기서는 양쪽 모두 조회 상태를 별도로 관리합니다.

## 실제 기록에서는 무엇이 달랐나

고정한 소스로 Chrome에서 열 번 실행해 HTTP 응답 28건을 기록했습니다. 아래는 각 사례의 마지막 확인 지점에서 읽은 값입니다. 모든 중간 DOM이 한 번에 같은 상태로 바뀌었다는 뜻은 아닙니다.

| 사례 | 상태만 보호 | 쓰기도 보호 | 조회 상태 |
| --- | --- | --- | --- |
| 늦은 성공 | 표시 수량 `7` | 표시 수량 `3` | 둘 다 최신 시도 `failed` |
| 상품 변경 | B는 `12`, 떠난 A의 캐시는 `7` | B는 `12`, A 캐시는 `3` | 둘 다 `succeeded` |
| 창고 변경 | 서쪽은 `12`, 동쪽 캐시는 `7` | 서쪽은 `12`, 동쪽 캐시는 `3` | 둘 다 `succeeded` |
| A → B → A | 표시 수량 `7` | 표시 수량 `9` | 둘 다 새 시도 `succeeded` |
| 실패 뒤 캐시 읽기 | 표시 수량 `3` | 표시 수량 `3` | 둘 다 `failed` 유지 |

늦은 성공 사례에서는 두 방식 모두 이전 시도의 상태 갱신을 거절했습니다. 그런데 자동 쓰기 방식의 숫자는 `3`에서 `7`로 바뀌었습니다. 상태를 지킨다는 검사와 숫자를 지킨다는 검사는 같은 일이 아니었습니다.

A → B → A에서는 더 알아차리기 어려운 조합이 남았습니다. 최신 시도의 성공 상태는 그대로인데 숫자는 그 성공이 돌려준 `9`가 아니라, 이전 방문에서 시작한 요청의 `7`이었습니다. 성공 표시가 어떤 값에 대한 것인지 연결하지 않으면 상태와 데이터 각각은 그럴듯해 보여도 함께 읽을 때 다른 뜻이 됩니다.

반대로 상품·창고 변경에서는 현재 화면이 양쪽 모두 `12`를 유지했습니다. 차이는 떠난 범위에 남은 캐시였습니다. 직접 쓰기를 제한한 쪽은 이전 응답의 `7`을 버려 `3`을 남겼습니다. 이 결과를 무조건 개선이라고 부르기는 어렵습니다. 다음 방문에서 그 응답을 활용할지 여부도 화면 정책의 일부이기 때문입니다.

## 범위가 같다는 것과 같은 방문이라는 것은 다르다

상품 A에서 B로 이동했다면 A의 늦은 응답으로 B의 조회 상태를 바꾸면 안 됩니다. A의 동쪽 창고에서 서쪽 창고로 바꾼 경우도 마찬가지입니다. 이 예제의 캐시 객체 키도 SKU와 창고를 함께 사용합니다. 요청의 범위 검사와 캐시의 객체 식별은 각각 맞아야 합니다.

A → B → A로 돌아오면 범위 문자열만으로는 부족합니다. 처음 A에 있을 때 시작한 요청과 돌아온 뒤 시작한 요청은 상품과 창고가 같아도 화면의 다른 방문에 속합니다. 세대 번호는 이 차이를 남깁니다. 시도 번호는 같은 방문 안에서 먼저 시작한 요청과 나중에 시작한 요청을 구분합니다.

세대 번호가 유일한 구현 방법이라는 뜻은 아닙니다. 이 실험은 전체 실행에서 증가하는 시도 번호도 함께 검사하므로, 새 요청 뒤의 결과만으로 두 번호가 각각 반드시 필요하다고 증명하지 않습니다. 세대 전환은 다음 요청이 시작되기 전에도 이전 방문을 즉시 무효화하는 표현으로 사용했습니다.

이 규칙은 **나중에 시작한 시도에 화면의 결정권을 준다**는 선택입니다. 나중에 시작한 요청의 데이터가 서버에서도 더 최신이라는 증거는 아닙니다. 더 늦게 시작한 요청이 실패해도, 먼저 시작한 요청의 늦은 성공은 제외할 수 있습니다. 편리한 성공 결과를 버리는 비용까지 받아들이는 규칙입니다.

## 불리언 하나 대신 쓰기 권한을 맡으면

`no-cache` 뒤에 조건부 `writeQuery`를 두면, 응답을 화면에 반영할지 결정하는 지점을 직접 소유하게 됩니다. 하지만 자동 쓰기를 포기한 만큼 관리할 일도 늘어납니다.

- 다른 화면에서 유용할 수 있는 응답도 버릴 수 있습니다. 지금 보고 있지 않은 상품의 캐시를 미리 채워 두는 효과가 사라집니다.
- 부분 성공, 병합 규칙, 낙관적 갱신과 다른 쓰기 경로를 어떻게 다룰지 정해야 합니다. 이 실험의 완전한 상품 응답 하나보다 실제 앱의 쓰기 소유권은 넓습니다.
- 범위를 바꿀 때 기존 시도를 즉시 무효화해야 합니다. 나중 요청이 시작될 때까지 기다리면 그 사이에 도착한 이전 응답이 여전히 허용될 수 있습니다.
- 캐시 쓰기 직전 검사와 성공 상태 반영이 있다고 해서 트랜잭션이 생기는 것은 아닙니다. 쓰기 도중 예외가 나거나 다른 경로가 캐시를 바꾸면 별도 처리가 필요합니다. 예외를 실패 상태로 기록해도 이미 일어난 부분 변경을 되돌렸다는 뜻은 아닙니다.

React 공식 문서의 [Effect 정리 시 늦은 결과를 무시하는 예제](https://react.dev/reference/react/useEffect)는 결과를 적용할 조건을 두는 이유를 설명합니다. 이 실험에서는 그 판단을 공유 캐시를 쓰는 지점까지 옮겨야 하는지 묻습니다. 하나의 화면이 직접 관리하는 상태와 여러 구독자가 읽는 캐시는 보호해야 할 범위가 다릅니다.

## 확인해야 할 경계

로컬 서버가 요청의 도착을 확인한 뒤 응답을 명시적으로 풀어 주도록 구성합니다. 임의의 지연 시간을 믿고 “대체로 먼저 끝난다”고 가정하는 대신, 비교하려는 순서를 만듭니다. 이것은 선택한 완료 순서에 대한 실험이며 모든 경합이나 실제 네트워크 지연을 대표하지 않습니다.

서버는 하나의 로컬 GraphQL HTTP 서버입니다. 앞선 Federation 실험의 분산 요청 구조를 재현하지 않습니다. 같은 연산의 요청이 합쳐지지 않도록 `queryDeduplication: false`를 명시합니다. 응답을 기다리다가 취소하는 대신 끝까지 전달해, 도착한 응답의 쓰기 권한을 비교합니다.

조회 상태는 `useSyncExternalStore`, 캐시는 `useQuery`로 각각 구독합니다. 관측기는 `useLayoutEffect`에서 실제 DOM을 읽고, 확인 지점에서는 관측된 상태·값이 현재 store·cache와 일치할 때까지 기다립니다. 기다리는 코드가 화면을 렌더링하거나 값을 쓰지는 않습니다.

원본에는 확인 지점 사이의 DOM도 있습니다. 자동 쓰기 방식의 초기 조회에서는 `succeeded`인데 hook 데이터는 아직 없는 DOM이 먼저 기록됐고, A → B → A의 새 성공에서는 `succeeded`와 이전 수량 `3`이 함께 기록된 뒤 `9`가 나타났습니다. 독립적인 두 구독이 같은 commit에 반영된다고 가정할 수 없었습니다. 직접 쓰기 방식의 이번 기록에서는 해당 조합이 나타나지 않았지만, 이를 모든 중간 상태의 원자성 보장으로 확대하지 않습니다. 이 관측은 사용자가 본 paint 횟수나 노출 시간을 측정하지도 않습니다.

해당 A → B → A 관측은 [원본 JSON](https://minjae-lee-kr.github.io/research/react-attempts/recording.json)의 `/browser/cases/6/domObservations/7`에서 읽을 수 있습니다. 바로 다음 관측에서 수량 `9`가 나타납니다. 배열 위치는 0부터 셉니다.

화면의 숫자, 독립적인 조회 상태, 현재 범위, 캐시와 실제 HTTP 결과를 함께 읽어야 합니다. 상태 표시만 보면 자동 캐시 쓰기를 놓칠 수 있고, 숫자만 보면 마지막 시도가 실패했다는 정보를 놓칠 수 있습니다.

어떤 방식도 현재 재고를 보증하거나 구매를 허용하지 않습니다. 응답의 서버 버전, 유효기간과 구매 직전 재검증은 별도 계약입니다. 여기서 비교하는 것은 선택한 화면의 시도 순서에 따라 **어떤 응답이 로컬 값을 바꿀 수 있게 할 것인가**입니다.
