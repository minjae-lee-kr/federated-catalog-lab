# Federation 설계에서 선택한 것과 감수한 것

[English](design.md) · [탐색기 실행 안내](federation-explorer.ko.md) · [프로젝트 소개](../README.ko.md)

## 1. Federation으로 책임을 나눠도 호출 비용은 남습니다

카탈로그는 상품 레코드를 소유하고, 재고는 같은 SKU를 기준으로 재고 정보를 보탭니다. 판매자 상세 정보는 별도 엔티티가 담당합니다. 카탈로그의 `Merchant` 선언은 `resolvable: false`를 사용합니다. 판매자를 가리킬 수는 있지만 그 필드까지 직접 조회한다고 선언하지 않습니다.

이 분리는 실행 순서에 의존성을 만듭니다. 카탈로그가 먼저 키를 반환해야 다른 서브그래프가 해당 엔티티를 조회할 수 있습니다. Federation이 이 순서나 원격 호출 비용을 없애 주지는 않습니다. 하나의 프로세스에 배열 세 개를 둔 이 예제만 보면 단일 GraphQL 서버가 더 단순합니다. 여기서는 Federation의 동작을 관찰하기 위해 경계를 나눴습니다.

게이트웨이를 시작하기 전에 로컬 SDL을 합성합니다. 실행 중 introspection으로 스키마를 찾아 배포하는 대신, 정확히 어떤 스키마가 합성되는지 테스트할 수 있습니다. 동적으로 정해지는 포트는 라우팅 URL에만 반영됩니다.

## 2. null 허용 여부가 실패의 범위를 정합니다

`products`는 목록 자체에 null을 허용하지 않지만 각 항목에는 허용합니다. 없는 SKU는 그 자리에 `null`을 반환하므로 입력 순서를 보존합니다. 상품명과 가격은 가상 카탈로그 레코드가 직접 제공하는 필수 값입니다.

`Product.availability`에는 null을 허용합니다. 재고 조회 실패가 상품 자체의 부재나 재고 0을 뜻해서는 안 되기 때문입니다. 수량 0은 품절이고, 재고 결과의 `null`은 미확인 상태입니다. 함께 반환하는 GraphQL 오류를 통해 의존성 실패와 의도적으로 만든 레코드 없음 시나리오를 구분합니다.

클라이언트에 `null`보다 자세한 정보가 필요하면 결과 union이나 최신성·조회 상태를 담은 타입을 선택할 수 있습니다. 클라이언트에 필요한 정보부터 정하고, 모든 필드를 별도 타입으로 감쌀지는 따로 판단합니다.

## 3. 로더 캐시는 요청 하나에만 속합니다

서브그래프는 HTTP 연산마다 DataLoader를 새로 만듭니다. 같은 연산 안에서는 중복 판매자 ID와 SKU가 배치 결과를 공유합니다. 요청 사이에 캐시를 공유하지 않으므로 이전 요청의 실패·오래된 값·접근 판단을 다음 요청이 재사용하지 않습니다.

배치 결과에는 요청한 키마다 같은 순서로 한 자리가 있어야 합니다. 구현은 조회 결과를 맵으로 만든 뒤 입력 키 순서에 맞춰 다시 배치합니다. 저장소가 입력 순서대로 반환한다고 가정하지 않습니다. 중복 키·없는 키·동시 요청을 테스트합니다.

실제 저장소와 권한 체계를 연결할 때는 로더의 실행 문맥과 캐시 키에 권한 판단을 반영해야 합니다. 이 프로젝트에는 사용자·테넌트 식별 모델이 없으므로 테넌트 간 격리를 검증하지는 않습니다.

## 4. 응답 기한은 기다림을 제한합니다

이 절은 기본 탐색기의 동작을 설명합니다. 별도 취소 실험에는 명시적인 취소 전달과 실행 슬롯을 너무 일찍 반환하는 잘못된 대조군이 있습니다. 그 실험의 결과와 한계는 [Cancellation Debt 설명](cancellation-debt.ko.md)에 정리했습니다.

게이트웨이 fetcher는 `AbortSignal.timeout`을 사용합니다. 재고에 지연을 넣으면 타임아웃이 발생하지만 카탈로그와 판매자 결과는 남습니다. 전송 타임아웃과 GraphQL resolver 실패는 다른 오류 코드로 표시합니다.

게이트웨이가 연결을 중단해도 하위 resolver는 계속 실행될 수 있습니다. 이 실험은 DB 취소, 요청 전체의 공통 기한, CPU 연산 중단을 구현하지 않습니다. 모든 서버가 같은 이벤트 루프를 공유하므로 이벤트 루프를 막는 작업은 타임아웃 처리도 지연시킵니다. 시간 관련 테스트는 넉넉한 범위에서 기한 적용을 확인하며, 서비스 수준 목표를 입증하는 측정이 아닙니다.

자동 재시도도 없습니다. 이를 추가하려면 재시도에 쓸 시간·횟수와 일시적 오류의 분류부터 정해야 합니다. 모든 서브그래프 오류를 재시도하면 하위 부하를 늘릴 수 있습니다.

## 5. 세 가지 검사는 서로 다른 질문에 답합니다

1. **스키마 합성:** 서브그래프 선언을 유효하고 실행 가능한 하나의 그래프로 합칠 수 있는가?
2. **API 스키마 비교:** 새 API가 기존 필드나 보장을 제거·완화했는가?
3. **쿼리 검증:** 저장된 클라이언트 쿼리의 선택과 변수 사용이 여전히 유효한가?

저장된 쿼리가 선택하지 않는 필드를 삭제하면 쿼리 검증은 통과해도 다른 소비자는 영향을 받을 수 있습니다. 출력 필드에 null을 허용하는 변경도 쿼리 구조는 유효하지만 생성된 클라이언트 타입의 가정을 깨뜨릴 수 있습니다. enum 값 추가는 기존 쿼리를 무효화하지 않더라도 모든 값을 나열한 클라이언트 분기에 영향을 줄 수 있어, 이 프로젝트의 계약 검사는 위험 변경도 검토 대상으로 처리합니다.

기준 스키마 비교만으로 동작의 의미, 정보의 최신성, 권한, 지연 시간, 업무 불변 조건까지 확인할 수는 없습니다. [소비자 영향 분석](schema-evolution.ko.md)에서도 이 경계를 유지합니다.

## 6. 관측 정보가 없다는 사실도 그대로 표시합니다

게이트웨이 응답은 요청별 서브그래프 호출 기록, 경과 시간, 수신한 서브그래프 HTTP 응답에 담긴 로더 배치를 포함합니다. 학습을 위한 계측이며 분산 추적 시스템이나 영속 감사 로그가 아닙니다. 기본 탐색기는 프로세스 전역에 이 기록을 모아 두지 않습니다.

타임아웃된 서브그래프의 배치 기록은 받을 수 없습니다. 화면은 이를 작업 0건으로 바꾸지 않고 “No batch result received”라고 표시합니다. 호출 기록 목록은 완료 순서이지 정밀한 시간축이 아닙니다. 관측한 밀리초 값은 실행 환경과 부하에 따라 달라집니다.

Apollo Server의 보고 플러그인은 비활성화했습니다. 별도의 Gateway 익명 텔레메트리도 생성자 실행 동안 `APOLLO_TELEMETRY_DISABLED=true`로 끕니다. 고정한 Gateway 버전은 생성자에서 이 값을 동기적으로 읽습니다. 중간에 `await` 없이 `finally`에서 호출자의 이전 환경 값을 복원하며, 테스트가 이를 확인합니다. 애플리케이션은 클라우드 인증 정보를 요구하거나 읽지 않습니다.

## 7. 작은 HTTP 어댑터를 직접 둔 이유

Apollo의 공개 API인 `executeHTTPGraphQLRequest`로 필요한 범위의 Node HTTP 어댑터를 구성했습니다. JSON POST만 받고 본문 크기와 Host·Origin을 검사하며 루프백에 바인딩합니다. listen 실패를 잡아 앞서 시작한 서버를 정리하고, 테스트에서 입력 경계와 정리를 확인합니다.

종료 시에는 새 연결 수락을 멈추고 유휴 연결을 닫습니다. 1초의 유예 시간이 지나면 본문을 끝내 보내지 않는 클라이언트를 포함해 남은 HTTP 연결을 닫습니다. stop을 여러 번 호출해도 같은 정리 Promise를 공유합니다. HTTP 연결을 정리하는 정책이며 JavaScript 연산이나 하위 작업을 강제로 중단하는 기능은 아닙니다.

범용 통합 패키지는 아닙니다. GET·APQ URL 처리, 업로드, GraphQL IDE는 제공하지 않습니다. 운영 서비스라면 유지보수되는 통합 도구를 먼저 검토하고 배포 환경의 접근 경계를 별도로 설정해야 합니다.
