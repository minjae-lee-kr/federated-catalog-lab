# Federated Catalog Lab

[English](README.md) · [한국어](README.ko.md)

같은 가상 상품·재고·판매자 API를 통해, 요청 실패가 서버와 클라이언트에 남기는 것을 살펴봅니다. 실제 Apollo Gateway와 HTTP 서브그래프를 사용한 독립적인 개인 실험입니다.

- **타임아웃 뒤에도 작업이 남는다면?** 아래 Cancellation Debt 실험에서 실행 슬롯을 언제 반환할지 비교합니다.
- **재고 조회 하나가 실패하면 무엇을 남길까요?** [부분 응답 비교](https://minjae-lee-kr.github.io/research/partial-data/)에서 배치 오류와 null 경계를 바꿔 봅니다. 재현: `pnpm batch-failure`.
- **다음 캐시 조회에 오류가 없으면 복구된 걸까요?** [클라이언트 캐시 실험](docs/client-cache.ko.md)은 오류 정책과 캐시 쓰기가 다음 조회에 미치는 영향을 다룹니다. 재현: `pnpm client-cache`.

- **오류가 사라지면 재확인도 성공한 걸까요?** [React 후속 실험](docs/react-recheck.ko.md)은 Promise, hook, 실제 DOM을 비교하고 확인 상태를 별도로 관리할 때의 비용을 다룹니다. [실행 방법](experiments/react-recheck/README.ko.md).

## Cancellation Debt

**응답은 끝났지만, 작업은 끝나지 않았다.**

상품 화면이 재고 응답을 기다리다 타임아웃돼도 재고 조회 작업은 계속될 수 있습니다. 이때 제한기가 그 작업의 자리를 돌려주면, 이전 작업이 처리 용량을 쓰는 동안 새 작업까지 받아들이게 됩니다.

네 가지 정책을 실제 HTTP 호출로 비교합니다. 실행 슬롯(permit)은 동시에 실행할 작업 수를 제한하기 위해 배정하는 자리입니다. 검사기는 이벤트로 작업 수와 점유 슬롯 수를 재구성하고 HTTP 응답과 대조합니다. 잘못된 정책에서는 **슬롯은 1개인데 작업은 4개가 실행 중**인 상황이 나타납니다.

**실행 슬롯은 작업이 끝날 때 반환해야 합니다.** 그래야 제한이 유효하지만, 사용자가 기다리지 않는 작업도 자리를 차지해 새 요청을 거절할 수 있습니다. 협력적 취소는 작업이 취소 신호에 반응할 때만 도움이 됩니다. 여기서는 타이머 작업을 사용하며 모든 서비스는 하나의 Node 프로세스에서 실행됩니다.

## 취소 실험 실행하기

Node.js **24.19.0 이상인 24.x 버전**과 pnpm **11.25.0**이 필요합니다. 설치 시 최소 버전을 확인하며, CI는 24.19.0에서 실행합니다. 인증 정보, Docker, 외부 서비스는 사용하지 않습니다.

```sh
pnpm install --frozen-lockfile
pnpm debt:ui
```

**http://127.0.0.1:4182/** 에서 네 가지 정책을 실행하고, 응답 이후에도 남은 작업과 원본 이벤트를 확인할 수 있습니다. 한국어·영어를 전환해도 선택한 정책과 펼쳐 둔 근거가 유지됩니다.

터미널에서는 `pnpm debt`를 실행하세요. 변경 사항이 없는 커밋에서 `pnpm debt:export`를 실행하면 `.local/cancellation-export/`에 읽기 전용 페이지, 원본 JSON, 파일 해시를 저장합니다. 이 명령은 외부에 게시하지 않습니다.

## 눈여겨볼 결과

같은 조회를 네 번 순서대로 시도합니다. **서브그래프 조회마다 160ms의 응답 기한**, **취소되지 않으면 1,000ms 동안 유지되는 타이머 작업**, 선택적으로 **두 개의 실행 슬롯**을 사용합니다. 성능 측정값이 아니라 현상을 드러내기 위한 실험 설정입니다.

| 정책                                              | 관측된 최대 작업 수 / 슬롯 수 | 드러나는 차이                                                          |
| ------------------------------------------------- | ----------------------------: | ---------------------------------------------------------------------- |
| 타임아웃만 적용                                   |                         4 / 4 | 기다림을 끝내도 작업은 계속됩니다.                                     |
| 요청 종료 시 슬롯 반환 — 의도적으로 잘못된 대조군 |                         4 / 1 | 슬롯 수만 정상으로 보여도 실제 작업은 제한을 넘을 수 있습니다.         |
| 작업이 끝날 때까지 슬롯 유지                      |                         2 / 2 | 실행량은 제한되지만, 남은 작업이 자리를 차지해 추가 요청을 거절합니다. |
| 작업 종료까지 슬롯 유지 + 협력적 취소             |                         1 / 1 | 취소를 지원하는 작업이 먼저 끝나고 슬롯을 반환합니다.                  |

표는 로컬 실행에서 관측한 결과이며 화면에 고정한 값이 아닙니다. 매 실행마다 예상한 반례가 실제로 나타났는지 검사합니다. 독립 검사기는 이벤트로 작업 수와 슬롯 수를 재구성하고 HTTP 응답과 연결하며, **취소 요청**과 **실제 취소 완료**를 구분합니다.

[기록된 이벤트 시간축 살펴보기](docs/observed-trace.ko.md): 두 정책의 차이와 원본 JSON, `ff47d27` 실행에서 재생성할 수 있는 그래프를 담았습니다.

**하나의 작업을 함께 기다린다면:** [정상 응답 뒤에 숨은 중복 실행](docs/shared-work.ko.md). 요청 취소와 작업 종료, 공유 등록 삭제를 분리해 재현합니다.

## 구현에서 볼 지점

- **취소 신호가 작업에 닿는 경로:** [실험 설명](docs/cancellation-debt.ko.md)에서 응답 종료부터 신호 전달, 슬롯 반환까지 따라갈 수 있습니다.
- **검사기 검증:** [독립 이벤트 검사기](src/cancellation-check.ts)는 누락된 작업 종료, 어긋난 요청 식별자, 일치하지 않는 카운터를 거절합니다. 실제 HTTP 대조군에서도 응답·작업 식별자를 바꿔 검사기의 검출 여부를 확인합니다.
- **실패 뒤에 남길 정보:** [키 하나가 실패할 때 달라지는 세 응답](docs/batch-failure.ko.md)은 개별 오류, 배치 전체 오류, non-null 필드를 실제 HTTP로 비교합니다. 세 실행 모두 Federation 스키마 합성과 쿼리 검증에 성공해도, HTTP 200 응답에 남는 데이터는 다릅니다. [기록된 상품 카드 비교하기](https://minjae-lee-kr.github.io/research/partial-data/).
- **스키마에서 소비자 코드까지:** [Federation 탐색기](docs/federation-explorer.ko.md)에서 엔티티 결합과 요청별 배칭을 살펴보고, [스키마 변경](docs/schema-evolution.ko.md)을 [타입 생성과 기존 소비자 코드의 컴파일](docs/consumer-impact.ko.md)까지 따라갈 수 있습니다.

[설계에서 선택한 것과 감수한 것](docs/design.ko.md) · [탐색기 구현 검토 순서](docs/review-guide.ko.md)

```sh
pnpm verify       # TypeScript, 스키마 계약, 테스트, 빌드
pnpm dev          # 선택 사항: 127.0.0.1:4181의 Federation 탐색기
```

## 확인한 범위

게이트웨이와 세 HTTP 서브그래프는 하나의 Node 프로세스에서 실행됩니다. 협력적 취소 조건에서만 타이머가 취소 신호를 받아 종료됩니다. DB 취소, CPU 작업 중단, 롤백, 분산 실행 제한, 실서비스 처리량을 입증하지 않습니다. 기한은 같은 호스트 시계를 쓰는 개별 서브그래프 구간에 적용되며 사용자 요청 전체의 시간 예산이 아닙니다. 소스 해시와 이벤트 검사는 재현을 돕지만, 악의적인 실행 환경이나 기록되지 않은 작업까지 검증하지는 않습니다.

데이터·시나리오·구현은 독립적인 개인 작업입니다. 회사 코드, 내부 설계, 비공개 수치나 장애 사례를 재현하지 않습니다. 실행 서버는 루프백 전용이며 공개 서비스가 아닙니다. 중간 심각도의 상위 의존성 권고 두 건이 남아 있으며, 노출 범위와 확인한 호출 경로는 [SECURITY.md](SECURITY.md)에 기록했습니다.
